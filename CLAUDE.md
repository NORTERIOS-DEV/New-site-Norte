# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Norte Rios institutional site: a Django REST backend (`norterios_site_backend/`) for a blog API, paired with a Vite+React frontend (`New-site-Norte/`). **This is a single monorepo** — both live under one root `.git`, with the frontend's original commit history preserved via `git subtree` (imported from its previous standalone repo). There is no root package.json/Makefile; the only thing that ties the two projects together at build/run time is the root `docker-compose.yml` + `.env`. The frontend has its own `New-site-Norte/CLAUDE.md` — read that when working there; this file covers the backend and the root-level orchestration.

No remote is configured on the root repo yet (the unification was done locally); `New-site-Norte/CLAUDE.md`'s mention of `github.com/NORTERIOS-DEV/New-site-Norte` refers to where the frontend used to live before the merge, not the current remote.

`docs/` holds ad-hoc Portuguese planning notes for the blog feature (`blog-norte-rios-contexto-tecnico.md` is the original design doc; `ideias.md`/`observações.md` are open questions/TODOs, not settled facts).

## Running the stack

```
docker compose up -d          # db (Postgres 16, :5442), minio+minio-init (:9002/:9003), web (Django, :8001->8000)
```

`web` runs `python manage.py runserver` in the container (see `norterios_site_backend/Dockerfile`) — a dev server, not gunicorn, even though gunicorn/whitenoise are in requirements.txt. There's no production entrypoint wired up yet.

**Two `.env` files exist and are easy to confuse:**
- Root `.env` (next to `docker-compose.yml`) — this is the one Docker actually loads (`env_file: .env` in `docker-compose.yml` resolves relative to the compose file, i.e. repo root).
- `norterios_site_backend/.env` — only read if Django is run locally outside Docker (`BASE_DIR/.env`); ignored by the dockerized `web` service.

Keep both in sync manually if you touch shared values (e.g. `CORS_ALLOWED_ORIGINS`) — Django settings fall back to it only when the corresponding OS env var isn't already set. On this machine specifically, port `5173` is already taken by an unrelated project, so Vite silently falls back to `5174` for the frontend dev server — `CORS_ALLOWED_ORIGINS` lists **both** `http://localhost:5173` and `http://localhost:5174` in both `.env` files so painel login works regardless of which port Vite actually picks. If login fails in the browser with no obvious error (works fine via `curl`/Postman against the API directly, but the painel's login form just shows "Usuário ou senha inválidos" for valid credentials), check the browser console for a CORS error and check `CORS_ALLOWED_ORIGINS` against the port Vite printed on startup — then `docker compose up -d --force-recreate web`.

**Env var changes require recreating the container, not just restarting it** — `env_file` values are baked in at container creation:

```
docker compose up -d --force-recreate web
```

There's also a stray Python 3.14 `venv/` at the repo root with the backend's dependencies installed into it, but no root-level `requirements.txt` and nothing references it — it doesn't match the Dockerfile's `python:3.12-slim` base and isn't part of the real dev flow. Use `norterios_site_backend/requirements.txt` with a venv created *inside* `norterios_site_backend/` if you need to run Django outside Docker.

**Run `npm install`/`npm run dev` from inside `New-site-Norte/`, never from the repo root.** This repo has no root `package.json` by design (see above) — but the PowerShell tool's working directory defaults to the repo root, and an `npm install <pkg>` run from there will happily create a throwaway root `package.json`/`package-lock.json`/`node_modules` (npm doesn't require an existing `package.json` to install into a directory) instead of erroring. This has happened before: `@dnd-kit/modifiers` (used by `SortablePhotoGrid.tsx`, see `New-site-Norte/CLAUDE.md`) ended up declared only in one of these stray root files, working by accident via Node's upward `node_modules` resolution rather than being in `New-site-Norte/package.json` where `SortablePhotoGrid.tsx` actually needs it. If you ever see a root `package.json`/`node_modules` appear, it's a mistake — move whatever got installed into `New-site-Norte/package.json` (`npm install <pkg>` from inside that directory) and delete the stray root files.

Frontend dev server: `npm run dev` in `New-site-Norte/` (port 5173, Vite default). It reads `VITE_API_BASE_URL` from `New-site-Norte/.env.development` (currently `http://localhost:8001/api`, matching the Docker-mapped backend port). Root `.env`'s `CORS_ALLOWED_ORIGINS` must match wherever the frontend actually runs, or `/api/*` fetches fail with a CORS error in the browser despite the backend returning 200.

## Backend architecture (`norterios_site_backend/`)

Django 6.1 + DRF project, four apps: `blog`, `galeria`, `accounts`, `uploads`.

- **Models** (`blog/models.py`): `Categoria` (nome, slug, `descricao`, `ativo`), `Autor` (nome, `nome_exibicao` — optional public display name, used as the public byline instead of `nome` when filled (see `nome_publico` below), foto, mini_bio, cargo, `formacao_especialidade` — optional academic background/specialty, separate from `cargo`, `instagram`/`linkedin` — optional `URLField`s, `ativo` — a standalone byline model; **not** the Django user; `nome_publico` is a property returning `nome_exibicao or nome`, used wherever the author's name is shown publicly) and `Post` (titulo, slug — auto-generated from titulo with collision suffixing in `save()`, resumo, `conteudo` — legacy HTML field, read-only from the painel, populated only on posts written before the TipTap editor existed, `conteudo_json` — `JSONField` holding the TipTap document, the source of truth for posts created/edited from the painel, `tempo_leitura_minutos` — auto-estimated from `conteudo_json`'s word count in `save()` via `blog/utils.py:estimate_reading_time` (200 wpm) whenever it isn't set explicitly, `imagem_capa` uploading to `blog/capas/%Y/%m/` (validated by `uploads/validators.py:validate_image_extension`/`validate_image_size` — jpg/png/webp, 5MB), `autor` FK to `Autor` (`PROTECT`), `categoria` FK (`SET_NULL`), `destaque`, `status` rascunho/publicado, `data_criacao`/`data_atualizacao` auto timestamps, `data_publicacao` auto-set to now on first publish, `meta_title`/`meta_description`/`og_image` — optional SEO overrides, see "SEO fields" below). Default ordering `-data_publicacao, -data_criacao`. `Post.autor` used to be a direct FK to the Django user model — migrations `0006`-`0009` swapped it to the `Autor` model (add new FK column → backfill → drop old FK → rename) without losing existing posts' authorship.
- **Status "agendado" (derived, not persisted)**: `Post.STATUS_CHOICES` only has `rascunho`/`publicado` in the database — there is no "scheduled" column value, and no Celery/cron in this stack to "promote" one. Instead, `Post.status_efetivo` (property) returns `'agendado'` when `status == 'publicado'` and `data_publicacao` is in the future, else returns `status` as-is; `Post.STATUS_LABELS` maps all three (including `'agendado': 'Agendado'`) to display labels. The public `PostViewSet` already filtered out future-dated posts before this existed, so a post "becomes" publicado automatically once its date arrives — nothing to promote. `PostPainelSerializer.status` is a `ChoiceField` accepting `agendado` as writable input; `validate()` requires a future `data_publicacao` when `agendado` is submitted, then rewrites `attrs['status']` to `publicado` before saving (the DB never stores `'agendado'`). `status_display`/`status_efetivo` on the serializer reflect the derived state. `PostPainelViewSet.get_queryset`'s `?status=` filter splits `agendado` (→ `publicado` + `data_publicacao__gt=now()`) from `publicado` (→ `publicado` excluding future dates) so the two don't overlap in list filters.
- **Destaque limit (up to 3)**: up to 3 posts can be `destaque=True` at once (changed from the earlier single-destaque exclusivity model — the old `post_unico_destaque` partial `UniqueConstraint` was removed by migration `0013`). `Post.save()` wraps the save in `transaction.atomic()`; when `self.destaque` is true it takes a Postgres advisory lock (`pg_advisory_xact_lock(730031)`, skipped on non-Postgres backends) to serialize the count check across concurrent requests, then calls `self.validar_limite_destaques(using)` before `super().save()`. `validar_limite_destaques()` raises a Django `ValidationError({'destaque': ...})` when 3 other posts are already featured; it's also called from `clean()` for form/admin validation paths. `PostPainelSerializer.create()`/`update()` catch that `DjangoValidationError` and re-raise as `serializers.ValidationError` so it surfaces as a normal DRF `400` instead of a 500. There is no more auto-unfeature-on-save behavior — the client must explicitly unmark a post before marking a 4th one.
- **SEO fields**: `Post.meta_title`/`meta_description`/`og_image` are optional overrides, left blank by default — never auto-copied from título/resumo/capa (that would go stale if the title changes later). Fallback is computed on read via properties `meta_title_efetivo`/`meta_description_efetivo`/`og_image_efetivo` (`self.meta_title or self.titulo`, etc.). The painel serializer exposes the raw (writable) fields; the public `PostDetailSerializer` exposes the *_efetivo values (read-only, via `SerializerMethodField`) so the frontend never has to reimplement the fallback.
- **Publish-readiness validation**: `PostPainelSerializer.validate()` blocks `status` from resolving to `publicado` (directly, or via the `agendado` translation above) unless `imagem_capa` is present (in the payload or already on the instance) and no image inside `conteudo_json` is missing `alt` text (checked via `blog/validators.py:contem_imagem_sem_alt`, a recursive walk of the TipTap JSON). This only fires when `status` is present in the request payload — a partial autosave PATCH that omits `status` never triggers it. `blog/validators.py` also has `validate_tiptap_document`, an allowlist-based structural check (node/mark types) run via `PostPainelSerializer.validate_conteudo_json` to reject a hand-crafted payload with an unrecognized node type (defense in depth — the actual HTML sanitization happens client-side via DOMPurify in `SafeContent.tsx`, not duplicated server-side with bleach/nh3, since `conteudo_json` is never the thing served as HTML and authors are already trusted `Gerenciador`-group users).
- **Views** (`blog/views.py`): `PostViewSet` and `CategoriaViewSet`, both `ReadOnlyModelViewSet` (list/retrieve only, `AllowAny`) — this is still the only *public* API. Content authoring now also has a real write API, but it's a separate authenticated surface; see "Painel de gerenciamento de conteúdo" below. `PostViewSet` filters the public queryset to `status=publicado` AND `data_publicacao <= now` (drafts and future-scheduled posts are hidden), supports `?categoria=<slug>`, and swaps in `PostDetailSerializer` (adds `conteudo` + `conteudo_json`) vs `PostListSerializer` (summary + `tempo_leitura_minutos`) based on action. `autor_nome` reads `obj.autor.nome_publico` (the `Autor` model's `nome_exibicao`, falling back to `nome`, not a Django user).
- **Pagination**: global `PageNumberPagination`, `PAGE_SIZE=10`, set in `settings.py` `REST_FRAMEWORK` — not per-view.
- **URLs**: DRF `DefaultRouter` in `blog/urls.py`, mounted at `/api/` → `GET /api/posts/`, `GET /api/posts/<slug>/`, `GET /api/categorias/`, `GET /api/categorias/<pk>/`, plus the DRF browsable root at `/api/`. Project-level `urls.py` also wires `/admin/`, `/ckeditor5/` (CKEditor's own upload endpoint — kept only for rendering/editing legacy `conteudo` HTML; new content no longer goes through it), and the `/api/painel/...` tree (see below).
- **Admin** (`blog/admin.py`): prepopulated slugs, list filters on status/categoria, `autocomplete_fields` on `categoria`/`autor`. This remains a full authoring surface (in addition to the painel now).
- **File storage**: `django-storages` + MinIO (S3-compatible) for `imagem_capa`, `Autor.foto`, painel image uploads, and legacy CKEditor inline images — nothing is written to local disk/`MEDIA_ROOT` in this setup.
- **CORS**: `django-cors-headers`, `CORS_ALLOWED_ORIGINS` read from env (see the `.env` gotcha above).
- **Migrations**: `blog/migrations/` — `0001_initial.py`, `0002_post_destaque.py`, `0003_autor.py`, `0004_categoria_descricao_ativo.py`, `0005_post_conteudo_json.py`, `0006_post_autor_novo.py`..`0010_post_autor_required.py` (the `Autor` FK swap, see above), `0011_autor_formacao_especialidade_autor_instagram_and_more.py` (adds `Autor.nome_exibicao`/`formacao_especialidade`/`instagram`/`linkedin`, all optional), `0012_post_meta_description_post_meta_title_post_og_image_and_more.py` (adds `meta_title`/`meta_description`/`og_image`; adds the image validators to `imagem_capa`; adds the `post_unico_destaque` partial `UniqueConstraint` — includes a `RunPython` data migration, `manter_apenas_um_destaque`, that normalizes any pre-existing posts that had `destaque=True` simultaneously before the constraint is applied, keeping only the most recently updated one), `0013_remove_post_unico_destaque.py` (drops that `post_unico_destaque` constraint — superseded by the application-level 3-post limit described above in "Destaque limit (up to 3)"). `galeria/migrations/` — `0001_initial.py`, `0002_categoria_album_categoria.py`. `accounts/migrations/` — `0001_gerenciador_group.py` (data migration, see below).
- **Tests**: `blog/tests.py` covers the painel API — publish-readiness (no capa / image without alt → 400), the `agendado` → `publicado` translation (past date rejected, future date accepted and `status_efetivo` reads back `agendado`), the `?status=agendado` vs `?status=publicado` queryset split, and the destaque limit (`test_permite_tres_destaques_e_rejeita_quarto_sem_desmarcar` — a 4th destaque is rejected with `400` until one is unmarked; `test_edita_destaque_no_limite_e_libera_vaga_ao_desmarcar` — unmarking one frees a slot for another). `uploads/tests.py` covers the upload endpoint's extension/size validation (gif rejected, >5MB rejected, valid jpg accepted). `galeria/tests.py` has its own coverage (model/thumbnail-generation/API tests, plus `GaleriaCategoriaFilterTests` — see below). Standard Django test runner applies: `python manage.py test` / `python manage.py test blog` / `python manage.py test galeria` / `python manage.py test uploads` (no pytest-django in requirements.txt).

### `galeria` app — photo albums

`Categoria` (nome, slug — separate from `blog.Categoria`), `Album` (titulo, slug auto-generated like `Post`, descricao, data_evento, capa opcional, `categoria` FK `SET_NULL`, publicado, ordem) and `Foto` (FK `album` CASCADE, imagem original, miniatura + imagem_media auto-generated, legenda, alt, largura/altura, ordem). On save, `galeria/services.py` uses Pillow to fix EXIF orientation, strip metadata, and re-encode the original, then generates a ~400px thumbnail and a ~1200px medium version as WebP — synchronously in `Foto.save()` (no Celery/Redis in this stack). `galeria/signals.py` deletes the image files from MinIO via `post_delete` (covers cascade deletes too, e.g. deleting an `Album`). Admin (`galeria/admin.py`) uses `adminsortable2` (PyPI: `django-admin-sortable2`, but the importable module is `adminsortable2`, not `django_admin_sortable2`) for drag-and-drop photo reordering, plus a custom bulk-upload view (`<int:album_id>/upload-fotos/`) for adding many photos at once. Read-only public API mounted at `path('api/galeria/', include('galeria.urls'))`: `GET /api/galeria/albuns/`, `GET /api/galeria/albuns/<slug>/`, `GET /api/galeria/albuns/<slug>/fotos/` (paginated), all filtered to `publicado=True`. `GET /api/galeria/categorias/` (`CategoriaViewSet`, `galeria/views.py`) filters to `Categoria.objects.filter(albuns__publicado=True).distinct()` — a category with no published album (or whose only albums are unpublished/draft) doesn't appear in this public listing, even though the category row itself still exists for the painel.

### Painel de gerenciamento de conteúdo — authenticated write API (`accounts`, `uploads`, `*_painel.py`)

A JWT-authenticated CMS surface lives entirely under `/api/painel/...`. The public endpoints above (`/api/...`, `/api/galeria/...`) are untouched and stay `AllowAny` — painel auth/permissions are opt-in per viewset, not a global default.

- **Auth** (`accounts/`, via `djangorestframework-simplejwt`): `POST /api/painel/auth/login/` (obtain token pair), `POST /api/painel/auth/login/refresh/`, `GET /api/painel/auth/me/` (id/username/email/name + `groups` + full `get_all_permissions()` list — the frontend uses the permissions list to gate UI). `SIMPLE_JWT` in `settings.py`: 30 min access / 7 day refresh, `ROTATE_REFRESH_TOKENS=True`. Every other painel viewset extends `accounts/viewsets.py:PainelModelViewSet` (`JWTAuthentication` + `IsAuthenticated` + `accounts/permissions.py:DjangoModelPermissionsWithView` — extends DRF's `DjangoModelPermissions` to also gate `GET` behind `view_<model>`, since these endpoints have no public/admin read-write split to fall back on). A `Gerenciador` Django group holding add/change/delete/view perms on `Post`/`Categoria`/`Autor`/`Album`/`Foto`/galeria-`Categoria` is created by the `accounts/migrations/0001_gerenciador_group.py` data migration and auto-assigned to any existing staff user.
- **Uploads** (`uploads/`): `POST /api/painel/uploads/imagem/` — generic authenticated image upload backing the TipTap editor's "insert image" toolbar command and its paste/drop handlers (extension allowlist + 5MB cap via `uploads/validators.py:validate_image_extension`/`validate_image_size` — jpg/png/webp only, **not** gif — reuses `galeria/services.py:process_new_image` for EXIF/format normalization, saves to MinIO under `blog/conteudo/`). `uploads/validators.py` is the shared validator module also used by `Post.imagem_capa`/`Post.og_image` (`blog/models.py`), so the same rules apply whether the image goes through this endpoint or a resource's own `ImageField`. Cover images (post/album), OG images, and author photos are plain `ImageField`s submitted with the resource's own multipart form and don't go through this endpoint.
- **Blog painel** (`blog/views_painel.py` + `serializers_painel.py` + `urls_painel.py`), mounted at `/api/painel/`: full CRUD on `posts`/`categorias`/`autores`. `PostPainelViewSet` supports filtering (`titulo`, `categoria`, `autor`, `status` — including the derived `agendado`, see "Status 'agendado'" above, `data_de`/`data_ate` against `data_publicacao`) and an ordering allowlist (default `-data_atualizacao`), plus `POST posts/<id>/publicar/` and `.../despublicar/` — both now go through `PostPainelSerializer` (`partial=True`) rather than setting `.status` directly on the model, so `publicar` inherits the same publish-readiness validation as a normal save. `AutorPainelViewSet.destroy` refuses to delete an author with posts (deactivate via `ativo` instead). `conteudo_json` accepts either a decoded object (JSON request body) or a JSON string (multipart body, needed whenever `imagem_capa` is uploaded in the same request) via `FlexibleJSONField`, and is validated against an allowlist of node/mark types (see "Publish-readiness validation" above).
- **Slug de `Post`**: `slug` é opcional em `PostPainelSerializer` (`required=False, allow_blank=True`) — se o cliente mandar vazio, `Post.save()` gera automaticamente a partir do `titulo` (ver `_generate_unique_slug` em `blog/models.py`); se mandar um valor, esse valor tem prioridade e nunca é sobrescrito (`save()` só gera `if not self.slug`). `PostPainelSerializer.validate_slug` valida unicidade (excluindo a própria instância no update) e retorna `400` com `{"slug": [...]}` em caso de colisão. Como essa checagem não é atômica com o `save()` (TOCTOU), `PostPainelViewSet.create`/`update` também capturam `IntegrityError` do banco (constraint `unique=True` em `Post.slug`) e a convertem na mesma resposta `400`, cobrindo o caso raro de colisão por concorrência — sem isso, essa colisão vazaria como 500. Mesmo padrão de validação em `CategoriaPainelSerializer`, mas sem esse fallback de `IntegrityError` (fora do escopo até agora).
- **Galeria painel** (`galeria/views_painel.py` + `serializers_painel.py` + `urls_painel.py`), mounted at `/api/painel/galeria/`: full CRUD on `albuns`/`fotos`/`categorias`, plus `POST albuns/<id>/publicar/`, `.../despublicar/`, `POST albuns/<id>/fotos/upload/` (bulk photo upload, ordem continues after the current max; accepts optional `legenda`/`alt` form fields applied to every file created in that request — the frontend only ever sends one file at a time, so in practice this sets metadata on the single photo being created), and `POST albuns/<id>/fotos/reordenar/` (persists a full drag-and-drop reorder from `{"ordem": [id, ...]}`). `FotoPainelViewSet` only supports update (legenda/alt/imagem — `imagem` is writable on `FotoPainelSerializer` so a photo's image can be replaced via `PATCH`, reusing the same `Foto.save()` reprocessing/old-file-cleanup logic as a new upload) and delete — photos are only created via the album's upload action.

Common commands (inside the `web` container, e.g. `docker compose exec web <cmd>`, or locally with a venv in `norterios_site_backend/`):

```
python manage.py migrate
python manage.py createsuperuser
python manage.py test
```
