# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Institutional website for **Norte Rios** (educational management & training consultancy, Belém-PA, Brazil), in Portuguese (`pt-BR`). It is a **Vite + React 19 + TypeScript** single-page app, converted from three hand-authored static HTML pages. The originals are kept under `legacy/` for reference during the port (safe to delete once parity is confirmed).

## Commands

- `npm run dev` — Vite dev server (http://localhost:5173). **If a browser tab stays open while you run several `npm install`/`npm uninstall` in a row** (e.g. temporarily installing a tool like `playwright` and removing it again, or adding a few packages one at a time), each change to `package-lock.json` makes Vite re-optimize its dependency pre-bundle on the next request — an already-open tab can end up with pieces of two different pre-bundle generations loaded at once. For most deps this just causes a stale-module glitch fixed by a hard reload, but a couple of packages (notably `prosemirror-gapcursor`, pulled in by `@tiptap/pm`) register a global ProseMirror selection type at module-evaluation time and throw `RangeError: Duplicate use of selection JSON ID gapcursor` if evaluated twice in the same page — this is a dev-cache artifact, not an application bug. Fix: stop the dev server, delete `node_modules/.vite`, restart `npm run dev`, and hard-reload (not just HMR) the browser tab.
- `npm run build` — `tsc -b` (typecheck) → `vite build` → `postbuild` copies `dist/index.html` to `dist/404.html` (SPA fallback for GitHub-Pages-style hosts).
- `npm run typecheck` — `tsc -b` only.
- `npm run preview` — serve the production build.
- No test runner and no ESLint config. Type errors are the only automated gate.
- **First install / CI:** npm 11 blocks esbuild's postinstall by default (it's pinned in `package.json` `allowScripts`). If a fresh `npm install` warns and Vite then fails to start, run `npm approve-scripts esbuild` and reinstall.

## Deploy

`dist/` is fully static. `vite.config.ts` uses `base: '/'` (domain root, `norterios.com.br`). Client routes need the host to fall back to `index.html` (or `404.html`, which `postbuild` creates). Remote: `github.com/NORTERIOS-DEV/New-site-Norte`, branch `main` — historically updated via GitHub's web upload UI, so pull before pushing. No CI workflow exists yet.

## Architecture

`src/main.tsx` renders `<RouterProvider>`, imports the global stylesheets, and adds the `js` class to `<html>` unless `prefers-reduced-motion` is set (this class gates the reveal animation, mirroring the legacy behavior where no-JS visitors saw all content).

`src/router.tsx` — routes plus a permanent-style redirect from the legacy `/index.html` URL. `src/components/Layout.tsx` is the shared shell: `<Header>` + `<ScrollManager>` + `<Outlet>` + `<Footer>`.

Public routes (inside `<Layout>`): `/` (`HomePage`), `/blog` (`BlogPage`), `/blog/:slug` (`BlogPostPage`, lazy — see below), `/galeria` (`GaleriaPage`), `/galeria/:slug` (`GaleriaAlbumPage`), `*` (`NotFoundPage`). Painel routes (outside `<Layout>` — no public header/footer): `/painel/login` and everything under `/painel/*` — see "Painel de gerenciamento de conteúdo" below.

**Code-splitting via router `lazy`**: `blog/:slug` and every `/painel/*` route are registered with `lazy: () => import(...)` instead of a static `element`. This is deliberate, not cosmetic — `BlogPostPage` is the only public page that renders TipTap JSON (via `SafeContent`/`generateHTML`), and the whole `/painel` tree pulls in TipTap's editor, `@dnd-kit/*`, and `react-hook-form`. Keeping those `element`-based imports would put all of that in the main chunk every public page loads (home, blog list, etc.). Adding a new heavy dependency to a page always warrants checking whether it should stay behind a `lazy` route.

### Styling — global CSS, ported near-verbatim (do not convert to CSS Modules)

- `src/styles/tokens.css` — the brand `:root` custom properties (`--paper`, `--green-*`, `--teal-*`, `--orange-*`, `--forest`, `--ink*`, `--maxw`, `--r*`, `--shadow*`, font stacks), copied verbatim from the legacy `<style>`. Restyle by editing these, not literals.
- `src/styles/global.css` — every other rule from the legacy global `<style>` (header, hero, sections, footer, reveal, media queries). The dead `.blog`/`.post` block and the Fraunces font were dropped.
- **Class names in JSX match this stylesheet exactly** (`.pub .pcover img`, `.panel .pside h3`, `.sec-head`, `.reveal`, …). That coupling is deliberate — keep using the legacy class names when editing markup; the CSS is not scoped.

### Legacy inline `<script>` → React

The single IIFE that every legacy page ran is now split into:
- `hooks/useHeaderShadow.ts` — toggles `header.scrolled` past 8px scroll.
- `Header.tsx` — mobile-menu `useState` that toggles `body.nav-open` (+ `aria-expanded`); closes on route change and link click.
- `components/ServiceTabs.tsx` — the `.serv-tabs`/`.panel` tabs (keeps `aria-selected` + `.panel.active`; adds arrow-key navigation).
- `hooks/useRevealRef.ts` + `components/Reveal.tsx` — IntersectionObserver adds `.in` to `.reveal` (same threshold/rootMargin; adds `.in` immediately under reduced motion). `Reveal` is polymorphic via `as=` so the DOM tag matches the legacy markup.
- `components/Marquee.tsx` — renders its `items` twice for the seamless loop (once under reduced motion).
- Footer year is `new Date().getFullYear()` inline.
- `hooks/usePrefersReducedMotion.ts` backs the motion checks.

- **Rich text editor** (`src/tiptap/`, `components/painel/TipTapEditor.tsx` + `TipTapToolbar.tsx` + `TipTapBubbleMenu.tsx`): TipTap v3, schema in `tiptap/extensions.ts` (StarterKit — `heading: { levels: [1, 2, 3] }`, H4 is left out, no need for it — + Image, TextAlign, Placeholder, `CharacterCount`, Table*, and a custom `VideoEmbedEditor` node for YouTube/Vimeo). Content is persisted as TipTap JSON in `Post.conteudo_json` — not HTML. `tiptap/renderExtensions.ts` mirrors the same node schema *without* the React NodeViews (and keeps `heading: { levels: [1, 2, 3, 4] }`, one level wider than the editor's, so legacy posts with an `H4` already in their `conteudo_json` keep rendering correctly on the public site — the schema doesn't retroactively migrate old content, it only restricts what the toolbar can newly create), so `@tiptap/react` never has to load on the public site; `SafeContent.tsx` (replaces the old `SafeHtml.tsx`) uses it with `generateHTML()` to render `conteudo_json` to HTML for `BlogPostPage`, falling back to the legacy `conteudo` HTML string when a post predates the editor. `tiptap/videoUrl.ts` parses pasted YouTube/Vimeo URLs into `{provider, videoId}`. **Sanitization**: `SafeContent` runs the generated HTML through DOMPurify with `ADD_TAGS: ['iframe']` (needed for video embeds) but registers a `uponSanitizeElement` hook that strips any `<iframe>` whose `src` doesn't start with `https://www.youtube-nocookie.com/` or `https://player.vimeo.com/` — don't widen `ADD_TAGS`/`ADD_ATTR` for iframes without keeping that origin allowlist, or arbitrary iframe content becomes injectable via post content.
- **A brand-new, empty `TipTapEditor` must initialize with an explicit paragraph doc, not `content: ''`.** `@tiptap/starter-kit` registers the `Heading` node before `Paragraph` internally, so when `content` resolves to an empty string, ProseMirror's "default block type for an empty doc" picks `heading` instead of `paragraph` — the very first line a user types into a new post would silently become a heading. `TipTapEditor.tsx` works around this with a `DOC_VAZIO` constant (`{ type: 'doc', content: [{ type: 'paragraph' }] }`) passed as `content ?? DOC_VAZIO` instead of `content ?? ''`.
- **Never wrap `<TipTapEditor>` (or anything with its own interactive buttons) in a bare `<label>`.** `PostFormPage.tsx`'s "Conteúdo" field used to be `<label className="painel-editor-label">Conteúdo<TipTapEditor .../></label>` — a `<label>` with no `htmlFor` and no single associated form control delegates a click on any non-interactive descendant (e.g. text typed into the editor's contentEditable) to the first "labelable" element inside it per the HTML spec, which was the toolbar's first heading button. The practical symptom: clicking anywhere in the editor body silently fired the H2 toolbar button's `toggleHeading({level: 2})`, converting whatever paragraph was clicked into a heading — this was a latent bug since before this editor rework (the original schema always included level 2), just unnoticed because an empty-looking heading looks like a normal empty line until you inspect the markup. Fixed by making it a plain `<div className="painel-editor-label">` with an explicit `<span>Conteúdo</span>` instead of relying on implicit label text. The one-input cases elsewhere (`ImageDropInput` wrapped in a `<label>` for "Imagem de capa"/OG image, a `<select>` wrapped in a `<label>` for "Autor"/"Categoria"/"Status") are fine — there's exactly one labelable descendant each, so the delegation is unambiguous and is in fact *why* clicking those areas correctly opens the file picker / focuses the select.
- **BubbleMenu**: `TipTapBubbleMenu.tsx` imports `BubbleMenu` from `@tiptap/react/menus` (a separate subpath export in this TipTap v3 version, **not** from the `@tiptap/react` package root — it pulls in `@tiptap/extension-bubble-menu` as an explicit dependency, not just the optional peer `@tiptap/react` ships). `shouldShow` is `!state.selection.empty && editor.isEditable`, so it appears on any non-empty selection. Shows negrito/itálico/sublinhado/link, reusing `tiptap/linkPrompt.ts:promptForLink` (also used by the fixed toolbar's link button) so the two don't duplicate the `window.prompt`-based insert/remove-link flow.
- **Image `alt` text**: inserting an image via the toolbar's "Imagem" button prompts for alt text (`window.prompt`) right after upload, before `setImage({src, alt})` — an empty answer is allowed at insert time (publish-readiness validation catches it later, see `PostFormPage` above). Editing the alt of an image already in the document is a double-click on the image (`TipTapEditor.tsx`'s `editorProps.handleDOMEvents.dblclick`, not a toolbar command): it resolves the ProseMirror position under the click, prompts with the current alt pre-filled, and applies via `tr.setNodeMarkup`.
- **Paste cleaning**: `editorProps.transformPastedHTML` runs pasted HTML through `tiptap/pasteClean.ts:cleanPastedHtml` before TipTap converts it — strips `style`/`script`/`meta`/`link` tags entirely, removes `style`/`class`/`lang`/`dir`/`align`/`valign`/`id` and any `data-*` attribute from every element, and unwraps bare `span`/`font`/`o:p` wrappers (common Word/Google Docs noise) while keeping their children. Most style/class stripping already happens "for free" because ProseMirror's HTML parser only recognizes tags/attributes some extension's `parseHTML` rule maps to a node/mark — this util covers the residual noise plus one explicit safety rule: any `<img src="data:...">` in the pasted HTML is removed (never inserted as base64) and triggers a `toast.info` telling the user to use drag-and-drop or the toolbar's image button instead.
- **Image upload via paste/drop**: besides the toolbar's "Imagem" button, `TipTapEditor.tsx`'s `editorProps.handlePaste`/`handleDrop` catch a real image *file* (clipboard paste of a screenshot, or a dragged file — as opposed to pasted HTML containing an `<img>`, handled by paste cleaning above) and upload it via the same `uploadImagem` (`services/painel/uploadsApi.ts`) the toolbar uses, showing `toast.loading` → `toast.update` (success/error) and inserting the real returned URL at the drop position (`view.posAtCoords`) or the current selection (paste) — never base64.
- **Image insertion inside the editor** goes through `POST /api/painel/uploads/imagem/` (generic upload endpoint), not through the resource's own cover-image field.
- **Gallery photo management**: `components/painel/GalleryUploader.tsx` and `SortablePhotoGrid.tsx` (`@dnd-kit/core` + `@dnd-kit/sortable` drag-to-reorder, persisted via the album's `fotos/reordenar/` action). `SortablePhotoGrid`'s `DndContext` has `modifiers={[restrictToParentElement]}` (`@dnd-kit/modifiers`) so the dragged card can't be moved outside the bounds of `.painel-photo-grid` — without it, the card follows the pointer freely across the whole viewport. Both "Adicionar foto" (`GalleryUploader`) and "Editar" (`SortablePhotoGrid`'s per-photo "⋮" menu) share the same form: `components/painel/FotoFormModal.tsx` — a `.painel-modal-backdrop`/`.painel-modal` dialog (not self-portaled; each caller wraps it in its own `createPortal(..., document.body)`) with an `ImageDropInput` (drag-and-drop or click-to-select, single file — `existingImageUrl` shows the current photo when editing) plus legenda/texto alternativo inputs. It takes `exigirImagem` (only `GalleryUploader` passes it — a new photo requires a file, editing doesn't since the existing image can be kept), `initialLegenda`/`initialAlt`, and an `onSubmit({file, legenda, alt})` callback; since it's only ever rendered while its modal is open, it remounts fresh each time instead of needing manual reset logic. `GalleryUploader` calls `uploadFotos(albumId, [file], { legenda, alt })` (creates the photo with metadata already set, no separate edit step needed). `SortablePhotoGrid`'s edit modal calls `updateFoto(foto.id, { legenda, alt }, file)` — passing a `file` there now also replaces the photo's image (`PATCH` with multipart body; the backend's `FotoPainelSerializer` makes `imagem` writable on update, reusing `Foto.save()`'s existing reprocessing/old-file-cleanup), while passing `null` (user didn't drop a new image) updates only legenda/alt as before. The album detail grid (`.painel-photo-grid`) is a fixed 5-columns-per-row layout (3 cols ≤880px, 2 cols ≤600px — see `styles/painel.css`), not the old `auto-fill` responsive grid. Each photo card shows only its thumbnail plus an always-visible "⋮" button (`IconMore`, in `components/painel/icons.tsx`) that opens a small dropdown (`.painel-photo-menu`, built from scratch — no dropdown/portal library used) with "Editar" and "Excluir". Since the whole card is the dnd-kit drag handle, the menu wrapper and both modal backdrops call `stopPropagation` on `onPointerDown` to keep clicks there from starting a drag.
- **Styling**: `src/styles/painel.css` (painel-only chrome — sidebar, topbar, forms, tables) and `src/styles/tiptap.css` (editor content styles) are separate from the public site's `global.css`/`tokens.css` — the "don't convert to CSS Modules, match legacy class names" rule above is specific to the public site's ported stylesheets and doesn't apply to these.
- **Save/action feedback (toasts)**: `<ToastContainer>` (`react-toastify`) is mounted once in `main.tsx`, alongside the required `import 'react-toastify/dist/ReactToastify.css'` — without that CSS import the container renders unstyled/invisible, which is why toasts silently failed to show before this was added. Every mutation across the painel (`PostFormPage`, `CategoriasListPage`, `AutoresListPage`, `AlbumFormPage`, `PostsListPage`'s publicar/despublicar/excluir, `GaleriaListPage`'s publicar/despublicar/excluir, `SortablePhotoGrid`'s editar/excluir/reordenar foto, `GalleryUploader`'s upload) calls `toast.success(...)` in `onSuccess` and `toast.error(...)` in `onError`, in addition to any existing per-field (`setError`) or general (`erroGeral`) inline error state — the toast is the only feedback for actions that don't navigate/re-render in an obviously different way (e.g. publish/unpublish, delete, reorder). When adding a new mutation, follow this pattern rather than leaving a save/delete/status-change action with no `toast.success`/`toast.error` call.
- **New dependencies** for this area: `@tanstack/react-query`, `react-hook-form`, `@dnd-kit/{core,sortable,utilities,modifiers}`, `@tiptap/{core,react,starter-kit,html,pm,extension-image,extension-placeholder,extension-table,extension-table-row,extension-table-header,extension-table-cell,extension-text-align,extension-character-count,extension-bubble-menu}`, `react-toastify`. All `@tiptap/*` packages are declared as `^3.31.3` in `package.json` (same as the rest of the `@tiptap/*` stack — not pinned exactly, `--save-exact` wasn't used), but `package-lock.json` resolves every one of them to exactly `3.31.3` with zero divergence (`npm ls @tiptap/pm` shows a single deduped version across the whole tree). `@tiptap/extension-bubble-menu`/`extension-character-count` aren't otherwise installed in this repo (they're only optional peers of `@tiptap/react`) — when adding either, install with an exact version matching the rest (`npm install @tiptap/extension-x@3.31.3`), since letting npm resolve a newer patch for just one of them causes an `ERESOLVE` peer-dependency conflict against the rest of the stack.
- **Field error wrapper (`.painel-field`)**: every `<label>` that can render a `react-hook-form` field-level error span now has that `<label>` and its `{errors.x && <span className="painel-field-error">...}` wrapped together in a `<div className="painel-field">` (`styles/painel.css`: `display:flex; flex-direction:column; gap:0.35rem`). This matters specifically in `.painel-form-grid` (`PostFormPage`, `AlbumFormPage`) and `.painel-modal-grid` (`AutoresListPage`'s modal) because those are `display:grid` with 2 columns — without the wrapper, the label and its error span were separate grid auto-placement items, so an error appearing would shift every subsequent field into the wrong column/row instead of the error rendering under its own input. Applied for consistency to the flex-column forms too (`LoginPage`, `CategoriasListPage`'s modal). Fields with no error span (e.g. `categoria`/`status` selects, checkboxes, `ImageDropInput` labels) are left unwrapped. When adding a new field with a conditional error span, wrap it in `.painel-field` rather than leaving the label and span as siblings.
- **Textarea sizing**: every painel `<textarea>` has `resize: none` (`.painel-form-grid textarea`/`.painel-modal textarea` in `styles/painel.css`) — the browser's default free resize handle let users drag a textarea to any width/height, which broke the 2-column grid layouts. Where a textarea sits in the same `.painel-form-grid` row as an `ImageDropInput` ("Resumo" next to "Imagem de capa" in `PostFormPage`, "Descrição" next to "Imagem de capa" in `AlbumFormPage`), it gets `className="painel-textarea-match-image"` instead of a `rows` prop — that class sets `height: var(--painel-image-input-height)`, the same custom property (`:root`, 140px) that `.painel-image-drop`'s `min-height` uses, so the two boxes in that row always render the same height from one source of truth. Textareas with no image neighbor (`CategoriasListPage`'s "Descrição", `AutoresListPage`'s "Mini biografia") keep their plain `rows`-based height — only `resize: none` applies to them.
